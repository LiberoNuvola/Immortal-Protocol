Verify · failure boundaries

How can the system
be wrong?

A public threat surface is useful only when every threat has a defined boundary: what is detected, what must fail closed, and what evidence is still required.

01 · EXTERNAL INPUT

Stale or ambiguous Oracle

Detection requires freshness, publisher binding and unambiguous observation.

Response: fail closed / evidence required
02 · CANONICITY

Unverified Beacon

A published value must not be described as canonical merely because a publisher supplied it.

Response: trust mode boundary / B3 evidence open
03 · FINALITY

Unverified authority or ancestry

External finality claims require the relevant authority, ancestry and state-authentication evidence.

Response: reject unverified witness
04 · ECONOMIC SAFETY

Insufficient protected capital

An action cannot treat protected obligations as residual surplus.

Response: economic admission fails
05 · EXECUTION

Oversized transaction

Cardano transaction size is an architectural constraint, not a value to bypass.

Response: reject / redesign execution path
06 · GOVERNANCE

Economic side door

Authorization must not rewrite crystallized economic state or bypass the Economic Gate.

Response: reject outside authority boundary
07 · EVIDENCE

Non-reproducible result

A test or simulation is not promoted into ledger evidence without the required execution witness.

Response: evidence remains open
08 · REPLAY

Tampered decision record

Replay must bind to the exact canonical decision record and reject altered content.

Response: replay rejection
Design principle

Fail closed is not a slogan.

For each critical boundary, the meaningful question is: what exact input is accepted, what invalid condition is rejected, and what artifact proves that behavior? The public status page tracks where that evidence exists today.
