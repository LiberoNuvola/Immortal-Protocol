## Acceptance question

For a transition or scheduled execution to be classified as autonomous, the record must identify the trigger, authoritative observable proof, decision/authority boundary, concrete action, externally observable outcome, confirmation/finality condition, and behavior if nobody intervenes. A transition being representable as a pure function or a GitHub workflow being green does not establish permissionless on-chain execution or end-to-end liveness.

The normative State & Transition Specification defines the required order as: canonical state → authoritative-input verification → obligation/exposure derivation → candidate delta → complete post-state → `Safe` → `K_c` viability → accept/reject → atomic commit → history recording. It explicitly keeps safety and viability distinct, and treats safe stall as safety-conforming but liveness-degrading. See `docs/00-normative/04_STATE_TRANSITION_SPECIFICATION.md` §§1–4 and `docs/00-normative/07_CONFORMANCE_SPECIFICATION_FINAL.md` C5/C5b, C10, C14–C20.

## Evidence classes that must remain separate

- **Design:** a trigger or action is named in a specification.
- **Pure/reference function:** a state delta can be computed for typed input values.
- **Test/finite model:** selected positive/negative inputs and finite invariants pass.
- **Source proof/authoritative observation:** the input is authentic, fresh, canonical and final under the claimed source's trust model.
- **Ledger execution:** an actual transaction is accepted and observed on the specified network, with tx ref and post-state.
- **Autonomous liveness:** the next eligible step actually happens under the declared no-intervention assumptions and the outcome is recorded/resumed.

Evidence in a lower class does not imply any higher class. In particular, successful C6 finite-checker run #42 is mechanical certificate/packet evidence, not proof of a real-world transition, C4 economics, C5 ledger acceptance, or unattended C3 liveness.
