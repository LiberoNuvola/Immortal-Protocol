## Confirmed findings

### P0 — transaction/input binding is caller-asserted, not derived at the signing boundary

`Adapter/CARDANO/runtime/CardanoExecutionAdapter.ts` accepts `tx: unknown` and a separate `inputReferences` array. `submitEconomic()` validates the admission against the supplied array, then forwards the opaque transaction to `signTx()`. It does not independently prove that the input references supplied to the gate are the inputs encoded in the transaction actually signed.

The Issue call site in `src/mint.ts` uses `submitEconomic(tx, economicAdmission, [...], [...], 'Issue')`. This proves adapter routing, but not the identity between candidate transaction body and caller-supplied references.

**Closure criterion:** establish a stable, supported way to derive/canonicalize the actual candidate transaction inputs before signing, then compare them to the admission's bound references and action fingerprint. Do not rely on undocumented Lucid internals or caller-provided duplicates. If this cannot be done at the current TxBuilder boundary, move the check to a typed immutable candidate/finalized-body boundary before signing and document the trust boundary explicitly.

### P0 — freshness is not mandatory, and timestamp provenance was unsafe by default

`Adapter/CARDANO/observation/ExecutableLiquidityObservation.ts` exports `assertExecutableLiquidityObservationFresh(observation, currentObservedAt, maxAge)`. The inspected `assertEconomicAdmission()` invokes input binding and authenticated PrizePool correlation, but does not invoke freshness validation.

The production observation entrypoint `relayer/preprodIssueObservation.js` previously defaulted `observedAt` to `BigInt(Date.now())`. A timestamp generated by the local process is not proof of when the authoritative ledger/source snapshot was taken.

**Patch applied:** removed the implicit local-clock default. The function now requires an explicit `observedAt`, converts it to a non-negative integer timestamp, and forwards that value unchanged to the producer. Added a regression test that omission fails closed; existing tests that exercise other behavior now pass an explicit timestamp.

**Important limitation:** explicit input is not itself cryptographic proof that the timestamp is source-authenticated. Production callers and the producer contract still must be traced. The gate still lacks a governed freshness policy/current-time check at `submitEconomic()`. Do not invent a max-age constant. If no governing rule exists, keep live admission fail-closed pending a normative decision.

### P1 — digest syntax checks do not verify evidence content

The Issue bridge checks that EV1–EV7, Viability proof/evidence digests, and deployment evidence hash are 64 hex characters and that references are non-empty. This validates shape, not that the digest is recomputed from the referenced evidence or that the referenced source is authentic and retrievable.

**Closure criterion:** resolve each evidence reference through the approved evidence store/source, canonicalize the exact bytes under an existing format/version, recompute the digest, and verify the source/approval binding. No new hash convention or source authority may be invented in this patch.

### P1 — canonical transition evidence is a binding record, not a ledger observation

`CanonicalTransitionEvidence.ts` validates non-empty fields and hash-shaped fingerprints. `assertIssueAdmissionMatchesCanonicalEvidence()` correlates admission fingerprints with that record, but the record alone does not establish that the submitted transaction was included or that actual ledger post-state equals the declared post-state.

**Closure criterion:** after submission, correlate the returned transaction reference with an authoritative ledger observation and independently reconstruct/validate StateAfter against the expected canonical post-state. Until that evidence exists, classify the transition as submitted/unobserved, not confirmed.

## 2026-10-21 — Issue: wallet consent is not the same as economic authority

This review separates three distinct operations. It does not change the economic rules or any validator.

### Transaction authority map

| Boundary | What the current code does | Classification |
| --- | --- | --- |
| User wallet | `src/main.ts` starts the Issue request; `src/mint.ts` builds one candidate transaction; `CardanoExecutionAdapter` signs via the connected Lucid wallet and submits it. | User consent for spending and submission. It does not prove that the economic decision is correct. |
| Ticket mint policy | `plutus/MintPolicy.hs` checks one Counter input, a serial NFT name derived from the Counter, the Counter continuation to `n+1`, a valid Pending PrizeDatum, the exact Treasury payment valued through the configured Oracle State, and the B1 reservation in the same transaction. | On-chain structural and payment enforcement. |

### Finding

The buyer's wallet is the authority for authorizing the buyer's spend; the Cardano validators are the authority for accepting a transaction that satisfies their encoded rules. These are not interchangeable.

In the current implementation, however, the buyer's signature alone is not enough: the same Issue transaction advances the V3 carrier, and that validator requires a signature from the configured authority key. Therefore the external signer currently has a protocol-level veto over every Issue transition. The signed envelope also supplies the economic evidence inputs which the local Haskell producer evaluates. Calling this dependency only a "data provider" would understate its authority.

### Correct direction; no unsafe shortcut

To make Issue genuinely permissionless, removing the URL check or accepting unsigned witness fields is not sufficient and would be unsafe. A replacement must preserve the existing on-chain economic guarantees while removing discretionary trust in the signer. That requires an explicitly selected, verifiable design for both:

1. the V3 state transition (so the ledger can validate the authorized state transition without an indispensable operator signature); and
2. the economic decision evidence (so EEV, ProtectedCapital, freshness, obligation completeness and viability claims are either derived from authenticated state under already-governed rules or proven by an on-chain-verifiable proof).

Until that replacement is implemented and adversarially verified, the honest status is **atomic B1 sale checks on-chain; complete economic admission and V3 state advancement still authority-dependent**. Do not describe the current Issue path as fully permissionless/trustless.

No V3, Reveal, B1, B2 or economic semantics were changed by this audit. The existing carrier signature requirement remains in place; no key or signature check was bypassed.

### 2026-10-21 — Canonical Issue delta and trustless enforcement boundary

Classification: non-normative conformance analysis. This section records existing reference semantics; it does not create a new transition rule or authorize a V3 change.

#### Existing reference transition

`IMMORTAL/kernel/EconomicTransitionV3.hs` defines `transition profile s (Issue cid price)`. The existing reference relation requires:

- a class price defined by the configured `EconomicProfile` and exact equality between that canonical price and the requested `price`;
- the existing `EconomicKernel.classSaleable` predicate (class exists, is not above `CurrentActiveClass`, has `issued < cap`, and its `saleable` flag is true);
- the existing transition-validity preconditions and postconditions: profile validity, pre/post conservation, control-state validity, non-negative fields, and preservation of the monotonic `HighestClassEverActivated` rule.

For the selected class, the canonical reference delta is:

```text
tcsIssued       := tcsIssued + 1
tcsUnresolved   := tcsUnresolved + 1
tcsExposure     := tcsExposure + price
```

At state level, the same transition sets:

```text
v3UnresolvedReserve     := v3UnresolvedReserve + price
v3UnresolvedTicketCount := v3UnresolvedTicketCount + 1
```

All other class fields, other classes, crystallized liabilities, safety capital, reserve protection, mandatory future costs, control state and Jackpot state remain unchanged by this reference `Issue` transition. Do not encode a different delta in Plutus merely to close CI.

#### Existing gate composition

`PRE-RICH/onchain/PreRichEconomicAdmission.hs` composes the structural transition with projection into the universal state and the existing `EconomicGate`/viability predicate. Its inputs include `truthVerified`, `eevFresh`, `obligationsComplete`, candidate EEV, immediately executable liquidity, required immediate liquidity, and `allOmegaSuccessorsInCertifiedKernel`. The gate is a predicate over these inputs; its code explicitly says it does not manufacture truth, freshness, exhaustive obligations or a concrete-kernel certificate.

`PRE-RICH/onchain/PreRichIssueDecision.hs` computes a canonical reference-state serialization, pre/post hashes and an action fingerprint from `Issue`, pre-state hash and post-state hash. This establishes a reference computation path in Haskell; it does not, by itself, authenticate the supplied economic evidence or force the Cardano transaction to have the same post-state.

#### On-chain conformance gap

`PRE-RICH/onchain/V3EconomicStateCarrier.hs` currently receives an action envelope whose on-chain action class is a broad label (`Issue`, `Reveal`, `Claim`, `Expire`), plus decision/observation references, pre-state hash, action fingerprint, post-state hash and authority signature. The inspected validator checks carrier singleton continuity, unchanged carrier Value, state validity/version increment, endpoint hashes and the Ed25519 signature. It does not receive the canonical Issue class/price as explicit semantic coordinates and independently recompute the above Issue-specific field delta or verify that the fingerprint is the canonical reference fingerprint.

The current class-state checks (`classValid`) enforce shape, non-negativity and `exposure == unresolved * classPrice`, plus global reserve/count conservation; these invariants do **not** establish that an accepted carrier continuation changes only the permitted Issue fields by exactly the specified delta.
