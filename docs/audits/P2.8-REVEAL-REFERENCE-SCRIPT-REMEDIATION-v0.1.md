# P2.8 Reveal — transaction-size remediation

**Status:** ARCHITECTURE SELECTED / implementation + ledger evidence OPEN  
**Branch:** `work/immortal-green-closure`  
**Date:** 2026-09-26

## Problem

The historical exact Reveal construction measured 18,365 bytes against the 16,384-byte Cardano transaction-size ceiling.

The two compiled Plutus V2 scripts are large enough that embedding both validator witnesses in the Reveal transaction is the direct structural cause of the size pressure.

The remediation MUST NOT change validator semantics, datum/redeemer semantics, economics, or the Cardano protocol limit.

## Selected architecture

Use **reference-script UTxOs** for the two existing Reveal validators:

1. PRE-RICH PrizeValidator;
2. PRE-RICH B1PrizePool validator.

The reference scripts are published once as deployment infrastructure.

The Reveal transaction then:

- consumes the existing Prize UTxO;
- consumes the existing B1PrizePool UTxO;
- supplies both validator scripts through reference inputs;
- preserves the exact existing redeemers;
- preserves the exact existing continuing datums;
- preserves the exact existing economic admission witness;
- does not inline the validator CBOR in the Reveal transaction.

Lucid's transaction model supports placing a Plutus V2 script in a UTxO as a reference script and subsequently using that UTxO through `readFrom`. The repository already uses `readFrom` for authenticated reference state.

## Required deployment state

Each validator reference-script UTxO must be discoverable unambiguously.

The deployment record must bind:

`script hash → reference-script UTxO → exact script CBOR hash`

The script UTxOs are infrastructure, not economic state.

They MUST NOT be treated as authority for:

- ticket state;
- PrizePool accounting;
- Oracle state;
- control state;
- Treasury;
- governance.

## Reveal builder change

Current shape:

```
collectFrom(prizeUtxo, Reveal)
attachSpendingValidator(PrizeValidator)
collectFrom(poolUtxo, TicketRevealed)
attachSpendingValidator(B1PrizePool)
...
```

Target shape:

```
readFrom([prizeValidatorReferenceScript])
readFrom([b1PrizePoolReferenceScript])
collectFrom(prizeUtxo, Reveal)
collectFrom(poolUtxo, TicketRevealed)
...
```

The builder MUST fail closed if either reference-script UTxO is absent, ambiguous, or carries a script whose hash does not match the expected validator hash.

A fallback to inline scripts MUST NOT be used for the canonical Reveal path, because that would leave the >16 KiB construction operationally possible.

## Compatibility requirements

The redesign must preserve byte-for-byte semantic inputs where applicable:

- PrizeDatum schema;
- B1PrizePoolDatum schema;
- `Reveal(secret)` redeemer;
- `TicketRevealed(priceUsdm)` redeemer;
- Beacon-derived result;
- payout calculation;
- reserve release;
- crystallized liability increase;
- economic admission witness;
- signer and required reference inputs;
- continuing outputs.

Only the script-witness transport changes.

## Tests

### Structural

1. reference script UTxO is present;
2. reference script hash equals expected PrizeValidator hash;
3. reference script hash equals expected B1PrizePool hash;
4. missing reference script fails closed;
5. wrong reference script fails closed;
6. duplicate ambiguous reference scripts fail closed.

### Resource

The built Reveal transaction must be serialized and measured.

Required acceptance:

`serialized_tx_bytes <= protocol maxTxSize`

The repository's current resource audit must report the actual serialized transaction size, not merely static script sizes.

### Ledger

The exact transaction must then enter P2.8-B.1:

`tx.cbor + exact UTxO + PParams + EpochInfo + SystemStart`

→ native Cardano-ledger evaluation

→ ExUnits or ledger-originated failure.

## Important distinction

Reference scripts solve **transaction witness-size pressure**.

They do not by themselves prove:

- validator correctness;
- ExUnit feasibility;
- script execution success;
- ledger acceptance;
- full Reveal lifecycle conformance.

Those remain P2.8 evidence gates.

## Closure criterion

The Reveal-size blocker closes only when a real built transaction using the deployed reference scripts is:

1. below the actual protocol `maxTxSize`;
2. accepted/built without semantic fallback;
3. evaluated through the native Cardano-ledger path;
4. bound to exact transaction/context hashes in the evidence packet.

No increase to `maxTxSize` is permitted as remediation.
